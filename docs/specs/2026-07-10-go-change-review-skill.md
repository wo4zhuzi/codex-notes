# Go 双分支深度审查 Skill Spec

## 目标

设计一个可跨 Go 项目复用的个人 Skill `my-go-change-review`。用户提供原始 ref、开发 ref 和可选的改动目标后，Skill 基于两个固定 Git 快照审查本次开发分支引入的变化，重点回答：

1. 改动后的业务逻辑是否自洽。
2. 涉及事务和数据库锁的实现是否合理。

Skill 必须结合旧实现、直接关联代码、历史提交和验证结果判断风险，不能只检查 diff 语法或代码风格。

仓库中的模板必须作为可迁移的唯一源码，并提供经过测试的安装脚本。用户换电脑后只需 clone 本仓库，即可把指定模板安装到 `${CODEX_HOME:-$HOME/.codex}/skills/`。

## 背景与根因

普通 diff review 只能展示文本变化，无法直接回答以下问题：

- 新逻辑是否遗漏旧路径中的校验、状态约束、错误语义或副作用。
- 调用方是否仍依赖旧接口、旧返回值或旧执行顺序。
- 某段历史逻辑是否来自已修复的线上问题，本次改动是否让问题重新出现。
- 事务是否覆盖完整原子操作，Repository 是否发生 `tx` 逃逸。
- SQL 条件、索引、锁范围和加锁顺序是否可能造成死锁或大范围锁等待。

CodeGraph 曾作为候选方案，但它的索引对应建立索引时的工作树。要可靠比较两个 ref，需要维护两个隔离索引，复杂度和索引一致性风险高于本任务收益。因此最终方案不依赖 CodeGraph 或 Understand Anything，而是从真实 Git diff 出发，使用 Git、`rg` 和 Go 工具链定向扩展审查范围。

## 用户与使用场景

主要用户是需要在功能分支合并前进行深度审查的 Go 开发工程师。

典型场景：

- 新功能开发完成后，对比主干和开发分支。
- 模块重构完成后，确认外部行为是否保持一致。
- Repository、Service 或状态机改动后，检查事务一致性。
- SQL、批处理或并发更新改动后，检查锁范围、死锁和幂等风险。

## 输入契约

必填输入：

- `base_ref`：原始分支、tag 或 commit SHA。
- `head_ref`：开发分支、tag 或 commit SHA。

可选输入：

- `change_intent`：本次功能或重构目标、验收条件、明确不应改变的行为。

两个 ref 必须先解析为固定 commit SHA。审查基线使用：

```text
merge_base = git merge-base <base_ref> <head_ref>
review_range = <merge_base>...<head_sha>
```

缺少 `change_intent` 时，Skill 从 commit message、测试、注释和相关文档推断意图，并在输出中明确标记假设。无法确认的业务规则只能作为开放问题，不能作为确定缺陷。

## 权限与范围边界

### 允许执行

- 读取 Git diff、提交历史、源码、测试、配置和项目文档。
- 使用 `git show`、`git grep`、`git log -S/-G`、`git blame` 和 `git log --follow` 定向追踪新旧逻辑。
- 使用 `rg` 查找直接引用、接口实现、注册入口和配置引用。
- 使用项目已有 Go 工具链运行分层验证。
- 为隔离测试创建和清理临时快照。

### 默认禁止

- 修改业务代码、测试、配置或文档。
- 执行 `git checkout`、`git switch`、`git reset`、`git clean` 或改变用户当前分支。
- 自动执行 `git fetch`、安装工具、下载依赖或访问外部服务。
- 自动生成审查报告文件。
- 把风格偏好或缺少证据的猜测作为 finding。

审查完成后必须询问用户是否生成报告。只有用户明确确认后，才允许写入 Markdown 审查报告；这是只读审查的唯一可选写操作。

原 Skill 内部结构为：

```text
my-skills/my-go-change-review/
├── SKILL.md
├── agents/
│   └── openai.yaml
├── references/
│   ├── logic-consistency.md
│   ├── transaction-locking.md
│   └── severity-guide.md
├── scripts/
│   └── collect-review-context.sh
└── tests/
    └── test-collect-review-context.sh
```

职责划分：

- `SKILL.md`：定义触发条件、输入契约、只读边界、审查阶段和报告确认门。
- `agents/openai.yaml`：提供显示名称、简短说明和默认触发提示。
- `logic-consistency.md`：定义业务不变量、状态变化、错误路径和新旧行为一致性检查。
- `transaction-locking.md`：定义事务边界、`tx` 传递、隔离级别、锁范围、索引、死锁和重试检查。
- `severity-guide.md`：定义 finding 严重程度、证据状态和固定输出格式。
- `collect-review-context.sh`：确定性地校验 ref、计算 merge-base、收集提交、diff 和 Go module 信息，不作审查结论。
- `test-collect-review-context.sh`：在临时 Git fixture 中验证上下文收集脚本，不污染当前仓库。
- `my-skills/install-skill.sh`：把指定 `my-skills/<name>/` 模板复制到用户级 Codex Skills 目录；默认拒绝覆盖，`--replace` 时先备份旧版本。
- `my-skills/tests/test-install-skill.sh`：使用临时 `CODEX_HOME` 验证首次安装、重复安装拒绝、替换备份和输入校验。

## 审查执行流

### 1. 校验输入和仓库状态

1. 确认当前目录属于 Git 仓库。
2. 解析 `base_ref`、`head_ref` 和对应完整 SHA。
3. 计算 merge-base，拒绝无共同祖先的比较。
4. 记录 shallow clone、submodule、Git LFS、生成代码和未提交改动等限制。
5. 固定审查范围，保证后续分析不受分支继续移动影响。

### 2. 重建改动意图

1. 优先读取用户提供的 `change_intent`。
2. 补充读取 review range 内的 commit message、测试名称、注释和相关文档。
3. 将任务分类为新功能、重构或混合改动。
4. 明确业务目标、必须保持不变的行为和当前假设。

### 3. 建立变更清单

识别以下变化：

- 新增、删除、重命名和移动的文件。
- 变化的函数、方法、类型、接口和错误值。
- 配置键、默认值、序列化字段和数据库模型变化。
- SQL、事务封装、Repository、状态机和并发路径变化。
- 测试新增、删除和覆盖范围变化。

### 4. 定向扩展相关代码

默认从变更对象扩展到：

- 直接调用方。
- 直接被调用方或依赖。
- 直接接口实现方。
- 对应测试、mock、注册入口和配置引用。
- 与变更业务规则直接相关的历史提交。

只有发生以下变化时继续扩大范围：

- public interface 或共享数据类型变化。
- 持久化、序列化或配置契约变化。
- 事务、权限、并发或核心业务规则变化。
- 当前范围仍无法确定真实影响。

这套扩展规则不是通读整个仓库，而是沿明确依赖和业务证据逐层推进。

### 5. 审查逻辑自洽性

必须检查：

- 成功路径从前置条件、状态变化到最终结果是否闭合。
- 提前返回、错误分支和部分失败是否保持状态一致。
- 新旧实现中的校验、默认值、错误语义和副作用是否一致。
- 同一业务规则在 Handler、Service、Repository 和异步消费者中是否冲突。
- 新路径是否绕过鉴权、幂等、状态机、审计、日志或指标。
- 调用方是否仍按旧返回值、错误类型或执行顺序工作。
- 测试是否覆盖业务不变量，而不只是执行到新代码。

### 6. 审查事务与数据库锁

只要变更路径进入事务或数据库锁相关代码，就必须追踪完整事务边界，不受“直接关联”默认范围限制。

必须检查：

- 事务是否覆盖所有必须原子完成的读写。
- Repository 是否误用普通 `db`，导致部分操作逃逸出 `tx`。
- 提前返回、panic、commit 失败和 rollback 失败是否正确处理。
- 是否在事务内执行 RPC、HTTP、消息发送等慢操作。
- `SELECT ... FOR UPDATE`、更新和删除条件是否命中正确索引。
- 是否因缺少索引、范围过宽或批量更新导致大量行锁或表级影响。
- 不同业务路径的加锁顺序是否一致，是否可能形成死锁。
- 隔离级别是否能防止丢失更新、重复处理、超卖和写偏差。
- 死锁或锁等待超时后的重试是否具备幂等性。
- 嵌套事务、savepoint、读写分离和连接切换是否破坏预期语义。
- commit 后的外部副作用是否可能丢失，是否需要 outbox 等一致性机制。

Skill 自动识别 `database/sql`、GORM、`sqlx`、Ent、Bun 和项目自定义事务封装。只有从依赖、配置或 SQL 中确认数据库类型后，才能给出 MySQL 或 PostgreSQL 特定结论；否则必须标记为依赖环境确认的风险。

### 7. 补充审查维度

在两条核心审查链完成后，再检查：

- public API、错误类型和兼容性。
- `context.Context` 传递和取消。
- goroutine、channel、锁、竞态和资源释放。
- 性能退化、无界循环、N+1 查询和批处理规模。
- 权限、输入校验和敏感信息处理。
- 日志、指标、审计和故障定位能力。
- 测试缺口和文档同步需求。

## 分层验证策略

1. 先运行受影响 package 的测试和适用的 `go vet`。
2. 再验证直接依赖 package。
3. public interface、共享模型或核心基础组件变化时，扩大到对应 Go module。
4. 耗时、联网、依赖外部服务或可能改变外部状态的测试不自动执行。
5. 依赖未缓存导致 Go 命令需要联网时，停止该项验证并记录原因。

若 head 上出现疑似回归：

- 必要时在临时 merge-base 快照复跑相同命令。
- head 失败且 merge-base 通过，可作为本次回归的强证据。
- 两边都失败，标记为既有失败，通常不作为本次 finding。
- 无法复跑 base 时，只能报告疑似回归，不能下确定结论。

## 异常处理

- ref 不存在：停止并指出无法解析的 ref。
- 两个 ref 指向同一 commit：说明没有可审查改动并结束。
- 无 merge-base：停止并提示无关历史或浅克隆风险。
- shallow clone：允许继续，但必须说明历史分析不完整。
- 未提交改动：diff 仍基于固定 SHA；运行测试时使用临时 head 快照。
- submodule、Git LFS 或生成代码：标记未覆盖边界，不自行初始化、下载或生成。
- 验证失败：区分代码失败、既有失败、环境缺失和外部依赖不可用。

## Finding 分级与证据

严重程度：

- `P0`：可能造成大范围数据损坏、不可逆丢失或严重安全事故。
- `P1`：明确行为回归、事务逃逸、死锁、高概率大范围锁等待或生产故障。
- `P2`：特定边界下的逻辑错误、兼容性问题或具有明确触发条件的风险。
- `P3`：非阻断改进建议，必须与缺陷分开。

证据状态：

- `已确认`：可由 diff、源码、历史或验证命令直接证明。
- `高风险`：触发路径明确，但缺少数据库环境等运行证据。
- `待确认`：依赖业务规则或部署配置，只进入开放问题。

每条确定 finding 必须包含：

- head 或 base 上的文件和行号。
- 触发条件。
- 问题与实际影响。
- 直接证据。
- 不修改代码前提下的建议方向。

## 输出格式

审查结果按以下顺序输出：

1. 审查结论：不通过、有条件通过或未发现阻断问题。
2. Findings：按 `P0`、`P1`、`P2`、`P3` 排序。
3. 逻辑自洽性结论。
4. 事务与锁专项结论。
5. 验证命令和结果。
6. 开放问题、假设和未覆盖范围。
7. 固定询问：`是否生成审查报告？`

没有发现问题时，必须明确说明未发现阻断问题，同时列出验证缺口和残余风险。

## 审查报告确认门

用户确认后才生成报告，默认路径为：

```text
docs/reviews/YYYY-MM-DD-<sanitized-base>-to-<sanitized-head>.md
```

报告必须记录：

- 用户输入的 ref。
- merge-base、base 和 head 的完整 SHA。
- 改动目标与推断假设。
- 完整 findings。
- 逻辑自洽性和事务锁专项结论。
- 验证命令、结果和未覆盖范围。

ref 中的 `/`、空格和其他不适合文件名的字符必须转换为短横线。

## 测试设计

上下文收集脚本至少覆盖：

- 正常 base/head 和 merge-base 计算。
- base 分支继续前进后，不把基线新增提交混入开发 diff。
- ref 不存在、相同 ref、无共同祖先和 shallow clone。
- 文件新增、删除、重命名和多个 Go module。
- 工作树存在未提交改动时，收集结果仍只基于固定 SHA。
- 脚本执行前后 `git status --short` 保持不变。

Skill 行为验收至少覆盖：

- 新逻辑遗漏旧校验时产生带证据 finding。
- Repository 在事务中误用普通 `db` 时识别 `tx` 逃逸。
- 两条路径锁顺序相反时识别死锁风险。
- SQL 条件过宽或缺少索引证据时，不武断声称一定锁表。
- head 测试失败而 merge-base 通过时识别本次回归。
- 无问题时输出残余风险，并询问是否生成报告。

安装器至少覆盖：

- 首次安装后目标目录包含 `SKILL.md` 和 `agents/openai.yaml`。
- 未传 `--replace` 时拒绝覆盖已有 Skill。
- 传入 `--replace` 时先把旧版本备份到用户 Skills 目录下的 `.backups/`。
- 非法 Skill 名称和不存在的模板必须失败。
- 使用临时 `CODEX_HOME` 测试，不改动真实用户目录。

## 成功标准

- 只提供两个 ref 即可执行完整审查，改动目标为可选增强输入。
- 审查以 merge-base 为基线，不混入 base 分支后续提交。
- 不依赖 CodeGraph 或 Understand Anything。
- 不切换、修改或污染用户工作树。
- 优先回答逻辑是否自洽，以及事务和锁是否合理。
- 每个确定 finding 都有位置、触发条件、影响和证据。
- 未经用户确认不生成报告文件。
- 新电脑 clone 本仓库后，可用一条安装命令恢复 Skill。
- 当前实现验证完成后，使用同一安装器安装到用户级 Codex Skills 目录。

## 风险与取舍

- 不使用代码图谱降低了双快照维护成本，但接口动态分派、反射和注册式调用需要通过定向搜索、测试和人工语义审查补足。
- 不默认运行全量测试降低了大型仓库成本，但必须透明记录未验证范围。
- 不要求改动目标提高了使用便利性，但缺失业务上下文时只能基于代码证据判断，并明确列出假设。
- 数据库锁行为受数据库类型、隔离级别、索引和执行计划影响；缺少证据时必须保守分级，不能把可能性写成确定事故。

## 实现边界

后续实现阶段只创建上述 Skill、通用安装器、测试和必要的仓库说明，不扩展为自动修复、自动提交、CI 服务或 Pull Request 机器人。用户级安装只在全部验证通过后执行，不替代仓库中的模板源码。详细实施顺序和逐步验证命令由后续实现计划定义。
