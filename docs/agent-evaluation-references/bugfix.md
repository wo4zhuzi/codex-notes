# Bugfix 评估标准

## 适用边界

适用于修复已知 bug、测试失败、构建失败、运行时异常、兼容问题和线上问题复盘后的修复任务。

Bugfix 的核心要求是：修复必须能解释原始失败，不能只靠猜测或偶然通过。

## 阶段性评估

用于复现、定位或实现过程中，判断下一步是否成立。

检查重点：

- 是否复现了问题，或是否有足够日志、测试输出、错误栈作为证据。
- 根因是否来自真实代码、配置、日志或测试结果。
- 修复方向是否能解释原始失败。
- 是否存在多个可能根因，需要继续缩小范围。
- 当前局部验证是否支持继续推进。

阶段性通过只表示当前定位或修复方向可继续，不代表 bug 已修好。

## 交付评估

检查重点：

- 原失败用例是否通过。
- 是否新增回归测试，或已有测试是否能覆盖原问题。
- 相关测试集是否通过。
- 修改是否限制在根因相关范围内。
- 是否说明未覆盖的边界条件。
- 是否有自愈过程记录：失败、分析、修复、再验证。

推荐流程：

```text
复现失败 -> 定位根因 -> 补测试或确认已有测试 -> 最小修复 -> 验证失败用例 -> 验证相关测试集
```

## 停止线

出现以下情况应停止并交给人确认：

- 无法复现问题，也没有足够证据支持根因判断。
- 连续 3 轮验证失败仍无法收敛。
- 继续修改需要扩大范围到无关模块。
- 修复会改变 public API、数据结构、权限边界或兼容行为，但需求未确认。
- 继续操作可能覆盖用户已有未提交改动。

## 输出要求

最终输出应包含：

- 原始问题和复现方式。
- 根因证据。
- 修改文件和范围说明。
- 回归测试或等价验证。
- 验证命令和结果。
- 未覆盖边界和剩余风险。
- 交付状态。
